# 초대·방 문맥·게임 종료 후 재입장 작업 로그 (BE)

작성일: 2026-09-17

## 상태와 범위

사용자 요청으로 앞선 진단·수정 계획을 Task별 실행 전 로그로 분리했다. 각 Task의 현재 상태와 실행 결과는 아래 목록 및 개별 로그를 따른다. 초기 문서 생성 이후의 구현·검증 이력은 각 Task 실행 로그에 기록한다.

## 진단 기준선 — 이전 조사에서 수행

관련 기존 테스트 3개 suite, 37개 통과. 실제 resolveInvitationForCommand 함수를 저장소 대역과 실행했을 때 과거 세션 방 ID에서는 null, 문맥을 제거하면 현재 초대를 반환했다. 전체 createMessage/실DB 재현은 아직 하지 않았다.

새 방 초대 권한 오류와 수락 직후 이탈은 코드상 가능 경로를 확인한 상태다. 실제 제보의 원인으로 확정하지 않았다. 이번 문서 작성 중 제품 테스트를 재실행하지 않았다.

## 공동 실행 순서와 체크포인트

1. BE-1 / FE-1: 재현 조건과 메시지 내 대상 식별 규칙을 먼저 정한다.
2. BE-2 → FE-2, BE-3 → FE-3: 초대 대상과 새 방 문맥을 수정한다. 같은 파일을 수정하는 작업은 순차 진행한다.
3. 체크포인트: 수락·거절, 새 방에서 초대, 비방장 접근 거부가 모두 통과해야 한다.
4. BE-4 / FE-4: 서버 탈퇴와 클라이언트 소켓 종료를 같은 타임라인으로 검증한다.
5. BE-5 / FE-5: 같은 세 계정 시나리오로 통합 검증한다.
6. 최종 체크포인트: 실제 연속 플레이 결과, 관련 테스트, 빌드/타입 검사 결과와 미검증 항목을 기록한다.

## 공통 제약과 미확정 사항

- 본문은 `{ message }`를 유지하며 `clientAction`을 다시 도입하지 않는다.
- 서버의 OWNER + JOINED 권한 검사를 유지한다.
- 메시지에 넣을 초대 식별 표현은 BE-1 / FE-1에서 결정하고 두 로그에 동일하게 기록한다.
- 종료 후 재초대 검증은 C가 새 WAITING 방을 생성하는 흐름을 기준으로 한다. 제보 환경이 기존 방 재사용이었다면 BE-1 / FE-1에서 구분해 기록한다.
- 재접속 유예·TTL·DB 마이그레이션은 현재 계획에 포함하지 않는다. 필요하면 재현 근거와 계약 영향을 먼저 제시한다.
- Task 실행 후 해당 파일에 실제 변경 파일, 검증 결과, 미검증 사유, 커밋 여부, 다음 Task 영향을 갱신한다. 미수행 항목을 완료로 표시하지 않는다.
